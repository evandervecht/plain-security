// BRIEFING

Code security: what is inside the software we ship. Codebeveiliging: wat er in de software zit die wij leveren.

Code security means finding, fixing and preventing security flaws before software reaches production. It covers the code you write, the open-source parts you reuse, and the files that describe your servers and containers. Four places flaws hide, and how to tell which ones matter. Codebeveiliging betekent beveiligingsfouten vinden, herstellen en voorkomen voordat software in productie gaat. Het gaat om de code die u zelf schrijft, de open-sourceonderdelen die u hergebruikt, en de bestanden die uw servers en containers beschrijven. Vier plekken waar fouten zitten, en hoe u ziet welke ertoe doen.

Every application has flaws its developers did not intend. OWASP lists the most common ones in its Top 10:2025, and broken access control is number one: the software forgets to check whether you may see what you ask for. Automated code scanning is good at known patterns, such as text from a web form pasted straight into a database query. It is poor at business logic. It cannot know that invoice 1043 belongs to another customer.

Business impact: a missing access check leaks customer data quietly, through normal-looking requests, and no scanner warns you. We suggest two layers: scanning on every change for the known patterns, and a human review of any code that decides who may see or change what.

Elke applicatie bevat fouten die de ontwikkelaars niet bedoelden. OWASP zet de meest voorkomende op een rij in de Top 10:2025, en gebrekkige toegangscontrole staat op één: de software vergeet te controleren of u mag zien wat u opvraagt. Geautomatiseerde codescans zijn goed in bekende patronen, zoals tekst uit een webformulier die rechtstreeks in een databasevraag belandt. In bedrijfslogica zijn ze zwak. Een scanner weet niet dat factuur 1043 van een andere klant is.

Bedrijfsimpact: een ontbrekende toegangscontrole lekt klantgegevens stil, via normaal ogende verzoeken, en geen scanner waarschuwt u. Wij raden twee lagen aan: scans bij elke wijziging voor de bekende patronen, en een menselijke review van alle code die bepaalt wie wat mag zien of wijzigen.

Modern software is assembled. Your developers write the part that makes it yours and reuse open-source components for the rest: logging, web frameworks, file readers. When a flaw in one of those components is published, every application that ships the old version has it too, including yours. Dependency scanning compares the list of components in each release, its SBOM, with public vulnerability databases.

Business impact: once a flaw is public, attackers can search for every system running that version. You cannot fix what you do not know you ship. This step is about honest components with known holes; packages that are malicious on purpose are covered in the supply chain briefing.

Moderne software wordt samengesteld. Uw ontwikkelaars schrijven het deel dat het van u maakt en hergebruiken open-sourceonderdelen voor de rest: logging, webframeworks, bestandslezers. Wordt een fout in zo'n onderdeel gepubliceerd, dan heeft elke applicatie met de oude versie die fout ook, de uwe inbegrepen. Afhankelijkheidsscans vergelijken de lijst met onderdelen van elke release, de SBOM, met openbare kwetsbaarheidsdatabases.

Bedrijfsimpact: zodra een fout openbaar is, kunnen aanvallers zoeken naar elk systeem met die versie. U kunt niet herstellen waarvan u niet weet dat u het levert. Deze stap gaat over eerlijke onderdelen met bekende gaten; pakketten die bewust kwaadaardig zijn, staan in de briefing over de toeleveringsketen.

Servers, networks and storage are now often described in text files, infrastructure as code, and software is packed into container images. That makes them code too. One line that opens a storage bucket to the internet is copied to every environment built from that template. An image built two years ago still carries the operating-system libraries of two years ago. OWASP ranks security misconfiguration second in its Top 10:2025.

Business impact: one wrong setting becomes the default everywhere, and an old image brings old holes into new deployments. We suggest scanning templates and images before they are deployed, and rebuilding images on a schedule, not only when the application changes.

Servers, netwerken en opslag worden tegenwoordig vaak in tekstbestanden beschreven, infrastructure as code, en software wordt verpakt in containerimages. Daarmee zijn ook dat code. Eén regel die een opslagbucket voor internet openzet, wordt gekopieerd naar elke omgeving die met dat sjabloon wordt gebouwd. Een image van twee jaar geleden bevat nog de besturingssysteembibliotheken van twee jaar geleden. OWASP zet verkeerde beveiligingsconfiguratie op twee in de Top 10:2025.

Bedrijfsimpact: één verkeerde instelling wordt overal de standaard, en een oud image brengt oude gaten mee in nieuwe uitrol. Wij raden aan sjablonen en images te scannen vóór de uitrol, en images volgens schema opnieuw te bouwen, niet alleen als de applicatie verandert.

Scanners report every known flaw in every component, whether or not your software ever uses the flawed part. Teams get a list longer than they can fix, and sorting by severity score alone keeps it long. Three questions shrink it. Is the flawed code reachable in what we run? Is it being exploited now, according to the KEV catalogue? How likely is exploitation soon, according to EPSS? Suppliers can answer the first question for their product with a VEX statement.

Business impact: the flaw that is exploited today waits in the same queue as many that never will be. We suggest triage on reachability and active exploitation first. Ask for one number instead of the total: known-exploited flaws that are reachable in production, and how long each has been open.

Scanners melden elke bekende fout in elk onderdeel, of uw software het foute deel nu gebruikt of niet. Teams krijgen een lijst die langer is dan ze kunnen herstellen, en sorteren op alleen een ernstscore houdt die lang. Drie vragen maken hem korter. Is de foute code bereikbaar in wat wij draaien? Wordt hij nu misbruikt, volgens de KEV-catalogus? Hoe waarschijnlijk is misbruik binnenkort, volgens EPSS? Leveranciers kunnen de eerste vraag voor hun product beantwoorden met een VEX-verklaring.

Bedrijfsimpact: de fout die vandaag wordt misbruikt, staat in dezelfde rij als vele die dat nooit worden. Wij raden aan eerst te sorteren op bereikbaarheid en actief misbruik. Vraag om één getal in plaats van het totaal: bekende misbruikte fouten die in productie bereikbaar zijn, en hoe lang elk al openstaat.

The board-level point: code security is not a tool you buy but a habit on every change. The total number of findings tells you little. We suggest asking for two numbers: known-exploited flaws that are reachable in production, and how many days the oldest one has been open. De kern voor de directie: codebeveiliging is geen tool die u koopt, maar een gewoonte bij elke wijziging. Het totaal aantal bevindingen zegt weinig.
