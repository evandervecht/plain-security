php2shell. One request, and the web server is theirs. php2shell. Eén verzoek, en de webserver is van hen.

On 21 October 2026 the PHP project fixed two critical flaws, CVE-2026-109618 and CVE-2026-109619. They can let anyone on the internet run their own code on a web server, without logging in. NCSC-NL tracks them as php2shell. PHP is widely used for websites, and it also sits inside appliances and hosted products. Three questions matter: are you updated, is any of your PHP too old to get a fix, and where does PHP run that you don't manage yourself? Op 21 oktober 2026 heeft het PHP-project twee kritieke lekken gedicht: CVE-2026-109618 en CVE-2026-109619. Daarmee kan iedereen op internet eigen code uitvoeren op een webserver, zonder in te loggen. Het NCSC volgt ze onder de naam php2shell. PHP wordt veel gebruikt voor websites, en het zit ook in apparaten en gehoste producten. Drie vragen tellen: bent u bijgewerkt, is een deel van uw PHP te oud voor een fix, en waar draait PHP dat u niet zelf beheert?

Both flaws sit in PHP itself, not in your application. PHP says every installation that serves web requests is at risk, including PHP-FPM, Apache with mod_php, php-cgi, FrankenPHP and LiteSpeed. The risk is highest with mod_php: PHP has seen a working exploit in which one request, without a login, triggers the attack before any of your own code runs. Both flaws are rated 9.2 out of 10 on CVSS v4.0, which is critical. The fixed versions are 8.5.12, 8.4.27, 8.3.36 and 8.2.35.

Business impact: whoever runs code on the web server can read what the website reads: customer data, database passwords, payment flows. That can also be a personal-data breach, which the GDPR requires you to report within 72 hours. PHP is clear that settings in php.ini reduce some attack paths but do not make a server safe; only the update does. CERT-EU reports that proof-of-concept code is circulating and considers exploitation likely. On 21 October 2026 neither flaw was yet on CISA's list of known exploited vulnerabilities.

Beide lekken zitten in PHP zelf, niet in uw applicatie. Volgens PHP loopt elke installatie die webverzoeken afhandelt risico, waaronder PHP-FPM, Apache met mod_php, php-cgi, FrankenPHP en LiteSpeed. Het risico is het hoogst bij mod_php: PHP heeft een werkende aanval gezien waarbij één verzoek, zonder inlog, de aanval start voordat er ook maar iets van uw eigen code draait. Beide lekken scoren 9,2 op 10 op CVSS v4.0, en dat is kritiek. De versies met de fix zijn 8.5.12, 8.4.27, 8.3.36 en 8.2.35.

Bedrijfsimpact: wie code draait op de webserver, kan lezen wat de website leest: klantgegevens, wachtwoorden van de database, betaalstromen. Dat kan ook een datalek zijn, en dat moet u volgens de AVG binnen 72 uur melden bij de Autoriteit Persoonsgegevens. PHP is duidelijk: instellingen in php.ini verkleinen sommige aanvalspaden, maar maken een server niet veilig; alleen de update doet dat. CERT-EU meldt dat er proof-of-conceptcode rondgaat en acht misbruik waarschijnlijk. Op 21 oktober 2026 stond nog geen van beide lekken op de CISA-lijst van bekend misbruikte kwetsbaarheden.

PHP 8.1 reached its end of life on 31 December 2025, and 8.0 and 7.4 earlier. The PHP project gives them no official release with this fix. It did publish minimal source patches for 7.4, 8.0 and 8.1, but someone has to build and test them. Linux distributions and long-term-support vendors may ship them as packages. Older versions get no patch from the PHP project at all. On PHP's own calendar, security support for 8.2 ends on 31 December 2026.

Business impact: a site on end-of-life PHP stays open until someone upgrades it or builds a patch. That is rarely a one-day job, because old PHP usually means an old application that breaks on a new version. So it is a project with a budget, an owner and a date. Until it is done, CERT-EU suggests isolating internet-facing systems that cannot be patched.

PHP 8.1 bereikte op 31 december 2025 het einde van zijn levensduur, 8.0 en 7.4 al eerder. Het PHP-project geeft ze geen officiële release met deze fix. Het publiceerde wel minimale broncodepatches voor 7.4, 8.0 en 8.1, maar iemand moet die bouwen en testen. Linuxdistributies en leveranciers van langdurige ondersteuning leveren ze mogelijk als pakket. Oudere versies krijgen van het PHP-project helemaal geen patch. Bedrijfsimpact: een site op verouderde PHP blijft open tot iemand hem bijwerkt of een patch bouwt. Dat is zelden werk van één dag, want oude PHP betekent meestal een oude applicatie die stukgaat op een nieuwe versie. Het is dus een project met een budget, een eigenaar en een datum. Tot het klaar is, raadt CERT-EU aan systemen aan het internet die niet te patchen zijn te isoleren.

PHP is not only on your own web servers. It runs in hosted websites and web shops, in content-management plugins and container images, and inside appliances, network devices and management interfaces. There you often cannot update PHP yourself; you wait for the vendor or the host. NCSC-NL keeps a public list of software products with a PHP dependency, and CERT-EU points to it. The list is still being expanded.

Business impact: the open question is rarely "did IT patch?". It is "which suppliers run PHP for us, and have they confirmed the update?". If you make a product with PHP inside and the flaw is actively exploited in it, the CRA requires you, as manufacturer, to report it: early warning within 24 hours, notification within 72 hours, via ENISA's Single Reporting Platform.

PHP staat niet alleen op uw eigen webservers. Het draait in gehoste websites en webwinkels, in plug-ins voor contentbeheer en in containerimages, en in apparaten, netwerkapparatuur en beheerinterfaces. Daar kunt u PHP vaak niet zelf bijwerken; u wacht op de fabrikant of de hostingpartij. Het NCSC houdt een openbare lijst bij van softwareproducten die PHP gebruiken, en CERT-EU verwijst daarnaar. De lijst wordt nog aangevuld.

Bedrijfsimpact: de open vraag is zelden "heeft IT gepatcht?". Het is "welke leveranciers draaien PHP voor ons, en hebben zij de update bevestigd?". Maakt u een product met PHP erin en wordt het lek daarin actief misbruikt, dan verplicht de CRA u als fabrikant tot melden: vroegtijdige waarschuwing binnen 24 uur, melding binnen 72 uur, via het Single Reporting Platform van ENISA.
