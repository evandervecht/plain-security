// BRIEFING

Terraform state: the map of everything you run. Terraform state: de kaart van alles wat u draait.

Many teams no longer build servers, networks and cloud accounts by hand. They describe them in text files, and a tool such as Terraform builds them. To know what it built, the tool keeps one file: the state. That file is a complete map of your infrastructure, it often holds passwords, and without it the tool no longer knows what it owns. Five things decide whether it is an asset or a liability. Veel teams bouwen servers, netwerken en cloudaccounts niet meer met de hand. Ze beschrijven ze in tekstbestanden, en een tool als Terraform bouwt ze. Om te weten wat hij bouwde, houdt de tool één bestand bij: de state. Dat bestand is een volledige kaart van uw infrastructuur, bevat vaak wachtwoorden, en zonder dat bestand weet de tool niet meer wat van hem is. Vijf dingen bepalen of het een bezit is of een risico.

With IaC, the code says what you want: three servers, one database, a network. When Terraform builds them, the cloud gives each one an ID. Terraform writes those IDs down in the state, by default a text file called terraform.tfstate. Next time, it compares code, state and reality, shows the difference as a plan, and changes only that.

Business impact: the state is how the tool knows what it is responsible for. Lose it, and Terraform sees an empty world: it may try to build everything a second time, or no longer tidy up what exists. A wrong or outdated state can make it change or delete the wrong thing. It is also a complete, current inventory of your estate, which is useful to you and to an attacker.

HashiCorp's documentation is clear: if a secret is in the configuration, Terraform stores it in the state and the plan. The state itself is a plain text file. Cloud storage encrypts it at rest by default, but AWS and Microsoft both decrypt it automatically for anyone allowed to read it. Encryption at rest protects against a stolen disk, not against a colleague, a pipeline or an attacker who holds read rights.

Business impact: everyone who can read the state can read the database passwords and keys inside it. That list is usually longer than anyone thinks: platform engineers, the pipeline, its runners, and in GitLab by default every Developer on the project. Newer Terraform and provider features can keep a secret out of the state altogether, where the provider supports them. A key held in a separate key service, such as KMS, adds a second gate: no key permission, no readable file.

De documentatie van HashiCorp is duidelijk: staat een geheim in de configuratie, dan slaat Terraform het op in de state en in het plan. De state zelf is een gewoon tekstbestand. Cloudopslag versleutelt het standaard, maar AWS en Microsoft ontsleutelen het allebei automatisch voor iedereen die het mag lezen. Versleuteling in opslag beschermt tegen een gestolen schijf, niet tegen een collega, een pipeline of een aanvaller met leesrechten.

Nieuwere functies van Terraform en providers kunnen een geheim helemaal buiten de state houden, waar de provider dat ondersteunt. NO LOCK · TWO WRITERS · A CORRUPTED MAPGEEN SLOT · TWEE SCHRIJVERS · EEN BESCHADIGDE KAART

If two people or pipelines change the same infrastructure at once, both write the state, and one overwrites the other. Locking stops that: the first one in holds the lock, the second waits. Some storage gives you locking automatically. With Amazon S3 it is switched off unless you turn it on. Versioning keeps every earlier copy of the state, so a bad write can be undone. HashiCorp highly recommends it for S3.

Business impact: a corrupted or overwritten state can lead Terraform to rebuild or remove production systems, and the repair is slow, manual work by your most senior engineers. Terraform has a command to break a stuck lock, with a warning in its own documentation to be very careful with it. Worth asking: is locking on, is versioning on, and has anyone ever restored an old state version?

Als twee mensen of pipelines tegelijk dezelfde infrastructuur wijzigen, schrijven ze allebei de state, en overschrijft de een de ander. Vergrendelen voorkomt dat: wie het eerst komt, houdt het slot, de tweede wacht. Sommige opslag geeft u dat slot automatisch. Bij Amazon S3 staat het uit tot u het aanzet. Versiebeheer bewaart elke eerdere kopie van de state, zodat een foute schrijfactie terug te draaien is. HashiCorp raadt dat voor S3 sterk aan.

Bedrijfsimpact: een beschadigde of overschreven state kan Terraform productiesystemen laten herbouwen of verwijderen, en het herstel is traag handwerk door uw meest ervaren engineers. Terraform heeft een commando om een vastgelopen slot te breken, met in de eigen documentatie de waarschuwing daar heel voorzichtig mee te zijn. Het loont om te vragen: staat vergrendeling aan, staat versiebeheer aan, en heeft iemand ooit een oude stateversie teruggezet?

THE BUCKET THAT HOLDS THE MAP NEEDS ITS OWN GUARDDE BUCKET MET DE KAART HEEFT ZIJN EIGEN BEWAKING NODIG

Terraform stores state in a backend: a storage location such as an S3 bucket or an Azure storage account. That storage has to exist before Terraform can use it. But teams want everything built by Terraform, including that storage. So what builds the bucket that holds the state of the thing that builds the bucket? The backend settings cannot even use variables, so they are fixed before anything runs.

Business impact: the bottom layer is often built once, by one person, and then forgotten. It holds the state for everything above it, so whoever can delete or change it can make the whole estate unmanageable. There are three common answers. Build it with a small separate Terraform setup and then move its state in, which Terraform supports with terraform init -migrate-state. Build it by hand or with the cloud's own tooling, and document it. Or use a hosted service that provides the storage, so only an account and access tokens remain to protect. Your call; we suggest choosing one on purpose and writing down who owns it.

Terraform bewaart state in een backend: een opslagplek zoals een S3-bucket of een Azure-opslagaccount. Die opslag moet bestaan voordat Terraform hem kan gebruiken. Maar teams willen alles door Terraform laten bouwen, ook die opslag. Wat bouwt dan de bucket die de state bewaart van het ding dat de bucket bouwt? De backendinstellingen kunnen zelfs geen variabelen gebruiken, dus ze liggen vast voordat er iets draait.

Bedrijfsimpact: de onderste laag wordt vaak één keer gebouwd, door één persoon, en dan vergeten. Hij bewaart de state van alles erboven, dus wie hem kan verwijderen of wijzigen, kan de hele omgeving onbeheersbaar maken. Er zijn drie gangbare antwoorden. Bouw hem met een kleine aparte Terraform-opzet en verhuis daarna de state erin, wat Terraform ondersteunt met terraform init -migrate-state. Bouw hem met de hand of met de eigen tooling van de cloud, en leg het vast. Of gebruik een gehoste dienst die de opslag levert, zodat alleen een account en toegangstokens overblijven om te beschermen. Aan u de keuze; wij raden aan er bewust één te kiezen en op te schrijven wie de eigenaar is.

The board-level point: you do not need to know Terraform to ask five useful questions. Where is our state kept, and is that one place or many? Who and what can read it, and is the list shorter than we fear? Are there passwords in it? If it were lost or corrupted tomorrow, could we restore it, and have we tried? And who owns the storage at the bottom that holds it all? Clear answers usually mean the map is in good hands.
